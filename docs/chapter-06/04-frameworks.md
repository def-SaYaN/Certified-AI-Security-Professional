# 6.4 Supply Chain Frameworks

!!! objective "In this section"
    - **SLSA** — levels, requirements, and how they map to ML
    - **SCVS** — the Software Component Verification Standard
    - How to use a maturity framework without turning it into theatre

---

## Why frameworks

Sections 6.1–6.3 told you *what* to worry about and *what* to check. A framework tells you **how
mature your practice is and what to improve next** — which is what you need when you have limited
budget and a sceptical audience.

Two are worth knowing.

---

## SLSA

**SLSA** (Supply-chain Levels for Software Artifacts, pronounced "salsa") is a framework for
securing **how software is built and delivered**. Its central concern is *build integrity*: can you
prove that the artefact you are running was produced from the source you think, by the build process
you think, without tampering?

### The core idea: provenance

SLSA's key output is **provenance** — verifiable metadata describing how an artefact was built:

- What source went in (repository and commit)
- What build process ran
- On what builder
- Producing what artefact (with a digest)

Signed provenance turns "we think this came from our pipeline" into "we can prove it".

### The levels

SLSA is organised into ascending levels of assurance. In broad terms:

| Level | Focus | Roughly means |
|---|---|---|
| **L0** | None | No guarantees |
| **L1** | Provenance exists | The build produces provenance describing how it was made |
| **L2** | Signed provenance, hosted build | Provenance is signed and generated by a hosted build service |
| **L3** | Hardened builds | The build platform resists tampering and provenance forgery |

!!! note "Levels evolve — the concepts do not"
    SLSA has been revised since its introduction, and the exact wording and numbering of
    requirements shift between versions. **Check the current specification at
    [slsa.dev](https://slsa.dev) for the authoritative detail.**

    What is stable, and what you should learn: **provenance, signing, hosted/trusted builders, and
    increasing resistance to tampering.**

### SLSA for ML

SLSA was written for software builds, but the concepts map onto ML training with only modest
translation:

| SLSA concept | ML equivalent |
|---|---|
| Source repository + commit | Training code, config, **and dataset version** |
| Build process | The training job (hyperparameters, environment, seed) |
| Builder | The training platform / cluster |
| Artefact | The **model weights** |
| Provenance | "This model came from *this* data + *this* code + *this* job" |
| Signed provenance | Cryptographically signed model attestation (Lab 6.5) |

!!! danger "Where the mapping strains, and why it matters"
    **Reproducibility.** SLSA assumes a build is reproducible — same inputs, same output, verifiable
    by rebuilding. ML training is frequently **not** reproducible: GPU non-determinism, random seeds,
    and data ordering mean you may not get bit-identical weights from the same inputs.

    So you often cannot *verify by rebuilding*. You must rely on **attestation** — a signed statement
    from a trusted builder that this artefact came from these inputs.

    That shifts the trust model: for software you can verify; for ML you frequently must trust the
    builder's signed claim. Which makes protecting the build platform (section 4.2) even more
    important.

### What to actually do

Practical SLSA-inspired steps for an ML pipeline:

- [ ] Version-control training code **and** pin dataset versions
- [ ] Run training on a **hosted, controlled** platform, not a researcher's laptop
- [ ] **Record provenance** for every model: source commit, dataset version, hyperparameters,
      environment, timestamp, builder identity
- [ ] **Sign** the model and its provenance (Lab 6.5)
- [ ] **Verify signatures** before deployment — and fail the pipeline if verification fails
- [ ] Harden the build platform; restrict who can trigger training and who can publish to the
      registry

## SCVS

The **Software Component Verification Standard**, from OWASP, takes a complementary angle. Where
SLSA asks *"can you prove how this was built?"*, SCVS asks *"how rigorously do you manage the
components you consume?"*

It is a structured set of verification requirements organised into domains, with three levels of
increasing rigour.

### The domains

| Domain | Concerned with |
|---|---|
| **Inventory** | Do you know what components you have? (SBOM) |
| **Software Bill of Materials** | Quality and completeness of that inventory |
| **Build environment** | Integrity of the pipeline that assembles things |
| **Package management** | How dependencies are fetched, pinned, verified |
| **Component analysis** | Vulnerability and licence analysis of components |
| **Pedigree and provenance** | Where components came from and how they were modified |

### The levels

- **Level 1** — baseline: you have an inventory and do basic analysis.
- **Level 2** — you verify integrity, manage provenance, and control your build environment.
- **Level 3** — comprehensive verification with strong assurance throughout.

!!! tip "SCVS is the better fit for a *consumer* of AI components"
    Most organisations do not train foundation models — they **consume** models, datasets, and
    libraries built by others (section 2.3).

    SLSA is primarily about *producing* artefacts securely. SCVS is about *consuming* them
    rigorously. **If you are downloading models rather than training them, SCVS maps more directly
    to your situation**, particularly its Inventory and Pedigree/Provenance domains.

### Applying SCVS thinking to AI components

| SCVS domain | AI question |
|---|---|
| Inventory | Do you have a list of **every model and dataset** in production? |
| SBOM | Is it machine-readable and kept current? (Lab 6.4) |
| Build environment | Is your training/fine-tuning environment controlled? |
| Package management | Are models **pinned to a revision** and hash-verified? |
| Component analysis | Are models **scanned** before use? (Lab 6.3) |
| Pedigree & provenance | Do you know the **base model** and the chain behind it? |

!!! warning "Most organisations fail the very first domain"
    Ask a team: *"list every model running in production, with its version and origin."*

    Very often nobody can. Models arrive through notebooks, get embedded in containers, and are
    pulled by scripts. There is no registry and no inventory.

    **You cannot secure a supply chain you have not enumerated.** Inventory is not a sophisticated
    control, and it is the one most commonly missing. If you are starting an AI supply-chain
    programme, start there.

## Using frameworks without theatre

A caution, because compliance frameworks invite box-ticking.

!!! danger "The failure mode: achieving a level without improving security"
    It is entirely possible to generate provenance nobody verifies, produce SBOMs nobody reads, and
    claim a level while remaining exactly as vulnerable as before.

    **The test of a framework is whether it changed a decision.** If your SBOM caused you to remove a
    dependency, or your signature verification blocked a deployment, it is working. If it produced
    artefacts that sit in a bucket, it is theatre.

Practical guidance:

- **Start with inventory.** You cannot do anything else without it.
- **Then verification.** Signing means nothing if nobody checks signatures — make verification a
  *blocking* pipeline step.
- **Then provenance.** Record how things were built, once the basics hold.
- **Pick the framework that matches your role** — SLSA if you produce models, SCVS if you consume
  them. Most readers of this course consume.

!!! question "Check your understanding"
    ??? success "What is provenance in the SLSA sense?"
        Verifiable metadata describing how an artefact was built — source repository and commit,
        build process, builder identity, and resulting artefact digest — ideally signed so it can be
        trusted.

    ??? success "Why does SLSA's reproducibility assumption strain for ML?"
        ML training is frequently non-deterministic (GPU behaviour, random seeds, data ordering), so
        the same inputs may not produce bit-identical weights. You often cannot verify by rebuilding
        and must instead rely on signed attestation from a trusted builder — which raises the
        importance of securing the build platform.

    ??? success "Which framework fits an organisation that downloads models rather than training them, and why?"
        SCVS. It focuses on rigorously verifying components you *consume* — inventory, package
        management, component analysis, pedigree and provenance — whereas SLSA is primarily about
        securely *producing* artefacts.
